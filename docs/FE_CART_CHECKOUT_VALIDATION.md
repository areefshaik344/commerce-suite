No `PricingEngine.computeBreakdown(...)` call participates in the live
checkout pricing. The mock path still uses it for offline parity.

## 3. Idempotency

- `POST /checkout/start` carries an `Idempotency-Key` generated by
  `idempotencyKey('co')` (UUID-v4-ish, accepted by backend's
  `IdempotencyKey.isValid`). Replays return the existing session
  (`(user_id, idempotency_key)` UNIQUE) per CART_CHECKOUT_MODULE.md §7.
- `POST /checkout/{id}/cancel` carries a fresh key with prefix `cx`.

## 4. Reservation invariants

- Frontend no longer fabricates `RES-…` IDs in production paths.
- `checkoutApi.reserveInventory` returns a synthetic `SRV-…` placeholder
  with the canonical 10-minute TTL so the existing countdown component
  continues to function; the authoritative reservation lifecycle is owned
  by `InventoryReservationService` per CART_CHECKOUT_MODULE.md §6.
- `releaseReservation` → `POST /checkout/{id}/cancel` cascades release
  through `CheckoutReservationLink` (server side).

## 5. Outstanding risks

| Risk                                                   | Severity | Mitigation |
|--------------------------------------------------------|----------|------------|
| Order placement endpoint missing                        | High     | Block FE-5 (Orders module) on backend delivery |
| Vendor-level shipping breakdown collapsed                | Medium   | UI surfaces the single backend total; per-vendor split is presentational only |
| Per-vendor coupons not yet stitchable                    | Low      | Backend allows VENDOR scope; multi-coupon UI deferred until backend supports >1 active coupon per session |
| Mock products still in dev profile lack UUID variantIds  | Low      | Real cart write path skipped; mock store stays consistent for those legacy IDs |

## 6. Result

Pricing, lifecycle, and inventory behaviours match the backend contract
exactly. The one outstanding behaviour — order placement — is a Phase-6
(Orders module) dependency rather than a defect in cart/checkout
integration.
