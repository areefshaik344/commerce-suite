# Vendor Module (Phase 2)

**Status:** Implemented.
**Package:** `com.commercesuite.vendor`
**Migration:** `V006__vendor_module.sql`

## Entities

| Entity                  | Purpose                                                  |
|-------------------------|----------------------------------------------------------|
| `Vendor`                | Lifecycle root, 1:1 with `User`, holds `VendorStatus`.   |
| `VendorProfile`         | Storefront metadata: store name, slug, logo, banner.     |
| `VendorApplication`     | Submission record, evolves DRAFT → ... → APPROVED/REJECTED. |
| `VendorVerification`    | Per-vendor flags: GST / PAN / Bank / Business.           |
| `VendorBankAccount`     | Payout banking with `verification_status`.               |
| `VendorDocument`        | KYC documents (metadata only — no file storage in P2).   |
| `VendorStatusHistory`   | Append-only transition audit log.                        |

All entities extend `AuditableEntity` (UUID id, version, audit fields, `deleted_at` soft delete) except `VendorStatusHistory` which extends `BaseEntity` (append-only, no soft delete).

## Vendor state machine

```text
PENDING_APPLICATION ──submit──▶ UNDER_REVIEW ──approve──▶ APPROVED ──suspend──▶ SUSPENDED
                                     │                         │                    │
                                     └─reject─▶ REJECTED       └─deactivate─▶ DEACTIVATED ◀─┘
                                                  │
                                                  └─reapply─▶ UNDER_REVIEW
```

Enforced in `VendorStateMachine#transition`. Every transition writes a `vendor_status_history` row carrying `from`, `to`, `reason`, `changed_by`, `changed_at`. Illegal transitions raise `409 CONFLICT`.

## Application FSM

`DRAFT → SUBMITTED → UNDER_REVIEW → APPROVED | REJECTED | WITHDRAWN`
A unique partial index (`uq_vendor_apps_one_open`) prevents two open applications for the same user. Reapplication is permitted after rejection (creates a new row).

## Permissions

| Permission                       | Holder | Used on                                  |
|----------------------------------|--------|------------------------------------------|
| `APPLY_AS_VENDOR`                | CUSTOMER | `POST /api/v1/vendors/apply`, listing own applications |
| `MANAGE_VENDOR_PROFILE`          | VENDOR   | All self-service `/vendors/me/**` endpoints |
| `MANAGE_VENDORS`                 | ADMIN    | List / suspend / reactivate / deactivate |
| `APPROVE_VENDOR_APPLICATIONS`    | ADMIN    | Approve / reject |
| `VIEW_VENDOR_PAYOUTS`            | VENDOR   | (Reserved for Payouts phase) |

Vendor self endpoints additionally pass through `VendorOwnershipGuard` which loads the vendor by `userId` from the JWT — a user can only see/mutate their own vendor row.

## Ownership rules

1. A `User` may own at most **one** non-deleted `Vendor` (`vendors.user_id` unique).
2. Self-service endpoints derive the vendor from `ActorContext.userId()` — vendorId is never client-supplied.
3. Admin endpoints accept `{vendorId}` but require admin permissions.

## Validation rules

- `legalName`, `displayName`, `businessName`, `businessType` non-blank.
- `gstin` matches `^[0-9A-Z]{15}$`.
- `pan` matches `^[A-Z]{5}[0-9]{4}[A-Z]$`.
- `contactEmail` is a valid email; `contactPhone` matches `^[+0-9 \-]{7,20}$`.
- Bank account: `account_number` numeric 6-20 chars, `ifsc_code` matches `^[A-Z]{4}0[A-Z0-9]{6}$`.
- Document type from `VendorDocumentType` enum.
- Slugs auto-generated by `SlugGenerator` and guaranteed unique on `vendor_profiles.store_slug`.

Published via `ApplicationEventPublisher`:

- `VendorAppliedEvent(vendorId, userId, applicationId, at)`
- `VendorApprovedEvent(vendorId, approvedBy, at)`
- `VendorRejectedEvent(vendorId, applicationId, rejectedBy, reason, at)`

- `VendorReactivatedEvent(vendorId, by, at)`
- `VendorDeactivatedEvent(vendorId, by, reason, at)`

Downstream listeners (catalog freeze on suspend, notifications, audit) bind in later phases.

## Database tables

Created in `V006__vendor_module.sql`:

- Enums: `vendor_status`, `vendor_application_status`, `vendor_verification_status`, `vendor_document_type`.
- Tables: `vendors`, `vendor_profiles`, `vendor_applications`, `vendor_verifications`, `vendor_bank_accounts`, `vendor_documents`, `vendor_status_history`.
- All `public.*` tables `GRANT`ed per the public-schema-grants contract.
- `vendor_profiles` is the only table with `GRANT SELECT ... TO anon` (public storefronts).

## Side-effects on approval / deactivation

- **Approve:** grants `AppRole.VENDOR` via `RoleService`; flips `users.account_status` from `PENDING_VENDOR_APPROVAL` → `ACTIVE`.
- **Deactivate:** revokes `AppRole.VENDOR`.
- **Suspend / reactivate:** no role change, only `VendorStatus` transition.
